# Speed, with a quality gate (November 2026)

Continues [prefill-100](prefill-100.md). Same machine: RX 9070 XT (RADV),
Ryzen 5 7600X, 61 GiB RAM, Samsung 980 PRO, Qwen3.8-Flash-Next UD-Q4_K_XL.

## The first-token check was a coin flip

`prefill-100` kept or dropped changes by whether the first token of the
507-token prompt stayed `</think>`. Three passes in one server process on
`740c09e`, `n_probs` 10:

| pass | first token | top two logprobs |
| --- | --- | --- |
| 1, cold | EOS | -2.0515, -2.4989 |
| 2, warm | `</think>` | -2.2823, -2.2880 |
| 3, warm | EOS | -1.9816, -2.4343 |

Passes 2 and 3 run the same binary on the same prompt. Pass 2's CPU misses
were admitted, so pass 3 ran 23742 experts on the device instead of 23568.
CPU and GPU expert math round differently, so the result depends on cache
state. The token is a near-tie. Changes dropped only for moving it
(`split_k` on the 4-row inject matmul, indexed `mul_mat_id`, the DSV4 HC
shaders) were never shown to be worse.

The repeat makes later chunks hit the cache, so the warm device path runs.
Script and text are rebuilt from `README.md`, `docs/qwen38-vulkan.md`,

and table rows removed.

- After decode the card is at 15.9 of 16.3 GB and GTT grows by about

## The cold prompt is bound by the consumer, not the drive

Cold 500-token prompt on `b2fdd54`, 7.8 s. The drive alone sustains
6.7 GB/s on random 1 MB direct reads at queue depth 8–16 (40 GB read,
43 → 47 °C). The engine reads at 5.67 GB/s inside a layer and 4.69 GB/s
averaged over the time it is busy.

| change | reads in flight | cold prompt |
| --- | --- | --- |
| ring 8 (shipped) | 7.4 | 7.8 s |
| ring 32 | 14.6 | 7.8 s |
| `--ssd-vram-budget 0`, every cold expert on the CPU | | 9.2 s, 4.8 cores busy |
| 1 GB budget, all 12698 cold experts on the per-expert GPU path | | 8.0 s |

A deeper ring doubles the reads in flight and changes nothing. The ring sits
idle for about 0.8 s waiting for the consumer to release slots. With a 1 GB
budget the per-expert GPU path summed 7.53 s for 12698 experts, 0.59 ms
each: three synchronized `mul_mat` calls plus a host SwiGLU between up/gate
and down. The work is a few microseconds of GEMM; the rest is submit and
wait. Batching a layer's GPU-assigned cold experts into a few submissions
should leave the cold prompt bound by the drive, about 5.8 s.

## Batching the cold misses on a device worker

A cold miss that finds a free host-cache slot is read straight into it.
Those bytes stay put until the slot is published, so the expert does not
have to be computed while it holds a ring credit. The stream now hands such
a miss to a worker thread and keeps the slot unpublished. The worker runs
the device layer path (`device_layer`, bucketed `mul_mat`, GPU SwiGLU and
reduce) on chunks of 32 to 128 experts while the CPU computes the ring
reads. The stream joins it after the last read, adds its sum into the
output, and only then admits the slots. A failed chunk falls back to the
per-expert consumer for every expert not yet done. A session mutex keeps
the stream thread's per-expert matmul and ahead calls off the worker's.

The first version ran the batch after the loop: 9.3 s. The worker made it
7.3 s. The chunks then spent 30–57 ms of 33–60 ms in `ggml_vk_write_ranges`:
a memcpy into staging at about 9.5 GB/s, then a 25 GB/s transfer. Four
memcpy threads gave the same 10 GB/s. The batch buffer is mapped ReBAR
memory, and a memcpy straight into it runs at about 24 GB/s (98 MB in
4 ms). With that, the GPU share that won moved to all of these misses:

| budget, GPU share | cold prompt |
| --- | --- |
| 256 MiB, per-expert path (`b2fdd54`) | 7807 ms |
| 256 MiB, worker, staged copy | 7325 ms |
| 512 MiB, worker, staged copy | 6521 ms |
| 1 GiB, worker, staged copy | 7782 ms |
| 512 MiB, worker, direct copy | 6456 ms |
| 1 GiB / 2 GiB, worker, direct copy | 6404 / 6392 ms |
| deferred misses ignore the budget, direct copy | 6399–6426 ms, 0.97 cores busy |

So these misses no longer count against `--ssd-vram-budget`; they use the
prompt batch buffer. Budget 0 still keeps every expert on the CPU.

Deferring a layer's few late misses (pass 2 of the warm prompt) added a
second device call with about 2.2 ms of fixed scatter and reduce after the
last read, and cost 30–50 ms per prompt. A layer now defers only if at
least 32 misses can go.

| | `b2fdd54` path (switch off, same binary) | now |
| --- | --- | --- |
| cold 500-token prompt, server | 7896 ms | 6391 ms |
| warm passes 2, 3 | 1556, 1551 ms | 1554, 1543 ms |
| server: cold A, warm A, then 128 generated | 7803 / 1550 ms, 10.66 tok/s, 1365 slots | 6384 / 1535 ms, 10.69 tok/s, 1367 slots |
| mixed A, A, B, A | 7876, 1567, 7124, 2998 ms | 6420, 1551, 7197, 3076 ms |

B and the last A miss into a full cache and read through the ring, so they
do not change. The one-shot completion is the one cost: its cold prompt

slot's `[1, ntokens]` weight to `[latent, ntokens]` before the MUL: 10 x
50 us of its 1.1 ms GPU time. MUL broadcasts the same values, so it is gone.

## The warm prompt is bound by PCIe

Each device layer scattered about 5000 expert-output rows into ten slot
buffers (3.3 ms) before the weighted reduce (1.0 ms). The down outputs now
start on whole rows of the batch buffer, beside one zeroed row, and the
reduce reads them in place: per slot a `get_rows`, the weight multiply in
place, and an in-place add into slot 0. Same products, same slot order.
It falls back to the scatter when the layout does not allow it.

Pass 2 of the warm prompt, same binary with and without it:

| | scatter + reduce | rows |
| --- | --- | --- |
| device layer total | 798 ms | 673 ms |
| ahead join wait | 161 ms | 286 ms |
| scheduler total | 1459.5 ms | 1459.7 ms |
| warm passes 2, 3 (two runs) | 1513, 1512 / 1511, 1505 ms | 1500, 1495 / 1496, 1504 ms |

The 125 ms moved into the wait for the next layer's ahead copy. That copy
is the warm prompt: pass 2 sends 38.7 GB of expert weights to the card at
about 27.5 GB/s (1.4 s of `set_us`). The warm prompt is at the PCIe bound
unless fewer bytes cross, for example by reading experts the decode cache
already holds. KL gate: 0.013964 ± 0.000921, same top 95.059 %;
mixed-cache perplexity run 37622 ms. ctest 123 of 123.

A decode cache that also took the 4.5 GB the prompt buffers hold while
idle (two ahead slots and the batch buffer) was tried by freeing them at
the phase change. The free memory the cache read barely moved (1411 slots
against 1380), and two runs gave 15.59 and 14.88 tok/s against 14.50:
decode varies by about ±0.5 tok/s between runs. Not kept. Lending those
buffers to the decode cache without freeing them is still open.

## The ahead copy skips experts the layer does not route

The ahead fill for layer L+1 starts before that layer's routing exists,
so it copies every cached expert of the layer's slice (about 283). A warm
99-token prompt routes about 177 distinct experts per layer, 256 tokens
about 223, 500 tokens about 265. Every warm prompt of 33 tokens or more
paid the full copy and took about 1.45 s.

The fill is joined at the start of the layer it is for, when that layer's
expert ids are known. The sink now passes the resident keys of those ids
first (`ahead_need`, `sink_cache::resident_keys`), and the fill skips any
other item it has not started. Experts it skipped and the layer needs are
uploaded from the host cache as before.

| warm prompt | before | after |
| --- | --- | --- |
| 99 tokens | 1467, 1451 ms | 1062, 1051 ms |
| 256 tokens | 1476, 1472 ms | 1281, 1274 ms |
| 500 tokens | 1498 ms | 1500 ms |

The math does not change. KL gate: 0.013112 ± 0.000881, same top
94.941 %; mixed-cache perplexity run 37663 ms. ctest 123 of 123.

## Decode prepare without a frequency tree

A decode token spent about 5.2 ms in the sink's `prepare`, 4 ms of it in
the RAM cache's `prepare`. Timers around its parts gave, per token: 2.6 ms
in the `count_decay2` bookkeeping and the hit and admission scans, and
1.1 ms in the slot ticket's room check.

`count_decay2` kept each layer's selection counts in a `std::map`. Every
layer of every token multiplied each node by the decay factor, up to 512
cold nodes per layer, and each eviction candidate cost a tree lookup.
The counts are now a dense vector of the layer's expert count. The
products are the same, so the scores are bit for bit what they were.
The vector is sized once per layer, so the per-layer allocation ticket
(a room measurement even when nothing grew) runs only then.

The slot ticket measured the room (cgroup and meminfo reads) even when
the layer committed no new slot, which is every decode layer once the
arena is resident. A zero-byte ticket could only refuse on unreadable
memory files, so it is skipped.

`prepare` went from 5.16 to 1.58 ms per token (1.07 ms of that is the
pack resolver). Interleaved decode runs, last 128 tokens:

| run | before | after |
| --- | --- | --- |
| 1 | 63.6 ms | 61.8 ms |
| 2 | 62.3 ms | 58.1 ms |
| 3 | 66.8 ms | 59.7 ms |
| mean | 64.3 ms (15.6 tok/s) | 59.9 ms (16.7 tok/s) |

Cache misses vary between runs of one binary (6172 to 7548 per 256
tokens, from prefetch and tier timing) and show no shift. The KL gate
runs a prompt only and never reaches this code. ctest 123 of 123.

## Resolving expert ranges without a search and a system call each

The rest of decode `prepare` was the pack resolver, 1.07 ms per token for
about 30 resolves per layer. Each one binary-searched the whole expert
index (about 17 `strcmp` probes over cold 192-byte entries), then asked
the kernel whether the descriptor was opened for direct I/O (`fcntl`).

The index now keeps each tensor's first entry. Expert e of a tensor whose
experts are one entry each sits at that entry plus e. When that entry has
the key and the one before it does not, it is the binary search's answer;
otherwise the search runs as before. The direct-I/O check, which lives
for one batch of resolves, no longer asks again about the descriptor that
just passed.

| per decode token | before | after |
| --- | --- | --- |
| resolve | 1070 µs | 328 µs |
| `prepare` | 1583 µs | 777 µs |

About 0.8 ms of a 60 ms token, smaller than run-to-run noise, so this is
measured by the timers rather than by the rate. ctest 123 of 123.

## Every layer gets a decode cache window

The decode cache binds a layer's slots 28 at a time (one window), and its
slabs were sized in whole slots: a 2 GB slab is 498 slots, 17 windows and
22 slots no window used. 1381 slots made 47 windows for 48 layers, so one
layer had no device slots and ran all ten routes on the CPU walk every
token. Slots are now counted in whole windows and slabs sized to whole
windows: 1372 slots, 48 windows and one overflow window. One layer's
hits are about 0.3 ms of a token, within run noise (60.1 ms, last 128).

### Lending the prompt buffers to the decode cache: measured, not built

The two ahead slots and the batch buffer (4.8 GB) sit idle during decode.
The cache sizes from the prompt's lowest free memory, so it cannot use
them. A temporary switch freed them at the first decode token. The
free memory the cache reads did not move at first: the kernel releases
the memory 5 to 45 ms after `vkFreeMemory`, and slabs allocated before
that went to GTT (2 GB of a 2212-slot cache sat in system memory and
decode got slower). Polling until the budget reflected the free gave
2492 slots, all in VRAM (15.9 GB used, GTT flat):

| last 128 tokens | 1372 slots | 2492 slots |
| --- | --- | --- |
| GPU routes | about 176 of 480 | about 327 of 480 |
| sink per token | 28.8 ms | 22.5 ms |
| token | 58 to 60 ms | 54.8 ms |

The first tokens of a decode wait about 40 ms each on drive reads either
way (an expert the prompt did not use is not in the RAM cache), so the
bigger cache did not cost a warm-up. Building this means returning the
lent slabs before every prompt and growing the cache again at decode.

## The decode cache borrows the prompt buffers

Built after the measurement above, without freeing anything: the two
ahead slots and the batch buffer have the decode cache's buffer type, so
their whole windows become overflow windows of layers that have none.
That is 1092 slots in 39 windows, 2464 in all. A decode token lends them
(`decode_cache::lend`); the prompt entries that touch them (`ahead`,
`mul_mat_batch`, `device_layer`) take them back first (`take_back`). That
drops their experts, waits out an upload in flight and acquires the ones
already copied. Nothing is freed, so no allocation waits for the kernel
to release memory or lands in GTT.

Interleaved 256-token completions, last 128 tokens (ms):

| lend | 58.7 | 54.9 | 58.4 | 58.5 | 54.1 | 54.9 | 56.6 |

about 25 to 17 ms. A server cycle of prompt and decode turns (500 + 128,

## Large mat-vec workgroups for long rows on RDNA

The mat-vec shader picks its workgroup size by vendor: NVIDIA and Intel
take the large one for `m <= 8192, k >= 1024`, AMD always the
subgroup-sized one. RX 9070 XT is detected as the RDNA3 class. Timed
with the perf logger (12 decode tokens), the large workgroup changed the
per-token totals of the decode shapes like this:

| shape | subgroup | large |
| --- | --- | --- |
| f32 4 x 10240 (combine injection) | 1094 µs | 509 to 614 µs |
| q8_0 2560 x 6144 | 1828 µs | 1606 µs |
| q8_0 320 x 10240 | 1200 µs | 1102 to 1117 µs |
| q8_0 640 x 2560 | 880 µs | 970 µs |

On the RDNA3 class the large workgroup is now used for `m <= 8192,
k >= 4096` and for `m <= 64, k >= 1024`. The perf-logged token went from
27.9 to 27.5 ms of GPU time. Interleaved runs, last 128 tokens: dense
wait 23.81/23.76/23.75 against 23.38/23.39/23.32 ms. Token times moved
with the GPU hit count (270 to 321 of 480), not with the change: each
build's runs generated different text in places, which moves the
routing and the decode cache's hits. `test-backend-ops -o MUL_MAT` on
Vulkan0: 940 cases OK. ctest 123 of 123. Prompts use the mat-mat path,
so the KL gate does not run this code.

## Where the CPU half of a decode token goes

The sink's phase line splits each token's expert walk into up/gate,
quantize and down, and counts the GPU hits. Per CPU-computed expert
(about 210 of 480 per token in these runs), up/gate takes 49 µs and down
30 to 32 µs. Up and gate are two q4_K 640 x 2560 matrices, 1.84 MB
together, so they stream at 38 GB/s. A 6-thread read benchmark on this
machine (AVX-512 loads over 4 GiB) peaks at 47 to 50 GB/s. The CPU walk
runs at about 80 % of the memory bandwidth, so it gets cheaper mainly
by moving experts to the GPU, not by faster CPU kernels.

### Poll after a parallel phase

Decode's resident walk is two parallel phases per layer: up/gate across
the hidden rows, then down across the output rows, with SWIGLU and
quantization on the coordinator between them. After a parallel phase
that was not the run's last, the participants parked at once, and the
coordinator parked while it waited for them. The down phase follows
within microseconds, so every layer paid a futex wakeup on each thread.
Both sides now poll for 200 µs first.

| --- | --- |
| park (3 runs) | 31.8, 31.8, 31.8 µs |
| poll 20 µs (2 runs) | 31.1, 30.9 µs |
| poll 200 µs (3 env runs, 2 final) | 29.7, 30.2, 29.9, 29.9, 29.9 µs |

## Two small-op removals in the dense decode graph

A dump of one decode layer's Vulkan graph (node, op, name, sources)
showed two patterns that cost dispatches without doing new work:

- `build_hc_mix` normed the streams, reshaped them to one row, and then
  multiplied by the gamma. The reshape sat between RMS_NORM and MUL, so
  the existing RMS_NORM+MUL fusion never matched, twice a layer. The
  gamma is now reshaped to the stream shape and expanded into the graph
  first, so MUL directly follows RMS_NORM. The fused shader computes
  `scale * x * w` in the same order as the two ops.
- The next layer's prefetch hint ranked the experts by softmax
  probabilities. Without a bias every supported gating function is
  increasing, so the logits give the same ranking; the hint now sorts
  them directly and the SOFT_MAX is gone (44 a token).

Perf logger, 12 tokens: RMS_NORM_MUL 78 to 168 a token, RMS_NORM 160 to
71, MUL 234 to 145, SOFT_MAX 44 to 0; GPU time 28.4 to 27.6 ms a token.
Interleaved runs, last 128 tokens, dense wait: 23.56/23.41/23.53 against
23.18/23.20/23.09 ms. Token times followed each run's CPU expert count

## SIGMOID into the MUL that takes it

Three gates are `mul(x, sigmoid(g))`: the DeltaNet output gate, the
attention output gate and the shared expert's one-value gate. On Vulkan a

## The DeltaNet state read and written in the cache

Each DeltaNet layer gathered its 3 MiB recurrent state with a GET_ROWS
(`build_rs`). GATED_DELTA_NET wrote the new state after its output, and a
CPY put it back in the cache. With those two dispatches skipped (and the
output wrong), the decode's GPU segments took about 1.6 ms less a token.

On Vulkan, `ggml_vk_fold_gdn_state` looks before each graph for a
one-sequence GDN whose state is reshapes of a GET_ROWS of the cache by
one id. Its new state must go only to one CPY into the cache; other
users may read only the attention output. That GDN reads its state from
cache row `ids[0]` and writes the new state to the CPY's destination
(`state_mode` in `gated_delta_net.comp`), and the GET_ROWS and the CPY
are skipped. Each invocation reads its own state elements and later
writes those same elements, so source and destination can be one row.
The cache tensors are not among the node's sources, so the barrier
check also tests them. A skipped node is never the last one the
command buffer closes on.

`test-backend-ops` has GATED_DELTA_NET_STATE: the gather, the op and the
copy in one graph, whose output is the attention output and the stored
state, read in place and from another row. With the shader reading row 0
in place of `ids[0]`, the three cases whose source row is not 0 fail.
The perf logger has GET_ROWS 135 to 103 and CPY 69 to 35 a token;
GATED_DELTA_NET 8.2 to 11.3 us, now that it reads the cache itself.

Interleaved runs, last 128 tokens, dense span 24.80/25.06/24.68 against
24.14/24.00/24.04 ms; tokens 51.8/54.7/49.7 against 52.2/50.3/51.9 ms.
KL gate 0.013703 ± 0.000921, same top 95.529 %. The KL gate's chunks are
one ubatch each, so it never carries a state from one ubatch to the
next. Perplexity at 2048 context in 512-token ubatches: 2.4525 ± 0.104
before, 2.4484 ± 0.104 after. The sink tests, 123 of 123. Server cycle:
the 500-token turns hash as the baseline's. Greedy decode text differs

decode runs' text is not compared.
