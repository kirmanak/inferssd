# Speed, with a quality gate (November 2026)

Continues [prefill-100](prefill-100.md). Same machine: RX 9070 XT (RADV),
Ryzen 5 7600X, 61 GiB RAM, Samsung 980 PRO, Qwen3.8-Flash-Next UD-Q4_K_XL.

## The first-token check was a coin flip

`prefill-100` kept or dropped changes by whether the first token of the
507-token prompt stayed `</think>`. Three passes in one server process on
`740c09e`, `n_probs` 10:

| pass | first token | top two logprobs |
| --- | --- | --- |
| 1, cold | EOS | -2.0515, -2.4989 |
| 2, warm | `</think>` | -2.2823, -2.2880 |
| 3, warm | EOS | -1.9816, -2.4343 |

Passes 2 and 3 run the same binary on the same prompt. Pass 2's CPU misses
were admitted, so pass 3 ran 23742 experts on the device instead of 23568.
CPU and GPU expert math round differently, so the result depends on cache
state. The token is a near-tie. Changes dropped only for moving it
(`split_k` on the 4-row inject matmul, indexed `mul_mat_id`, the DSV4 HC
shaders) were never shown to be worse.

## Quality gate

`llama-perplexity` with KL divergence against the CPU expert path
(`INFERSSD_PREFILL_GPU=0`). Text: three 2600-character blocks of the repo
docs, repeated once, 10 chunks of 512 tokens, `-c 512 -b 512 -ub 512`.
The repeat makes later chunks hit the cache, so the warm device path runs.
Script and text are rebuilt from `README.md`, `docs/qwen38-vulkan.md`,
`CONTRIBUTING.md` and this directory's `prefill-100.md` with fenced blocks
and table rows removed.

| | value |
| --- | --- |
| CPU reference PPL | 3.9055 ± 0.193 |
| `ef82e6c` GPU path vs CPU, mean KLD | 0.013271 ± 0.000973 |
| same top token | 94.980 ± 0.432 % |
| PPL(Q)/PPL(base) | 0.997933 ± 0.004528 |
| 99.0% KLD | 0.175790 |

A change keeps quality if its KLD against the same CPU reference stays at
or under the current path's, within the error, and the same-top rate does
not fall. The run is also a mixed-cache speed number: 5120 tokens in
40745 ms, 125.66 tok/s (the CPU path took 81128 ms).

## Where `ef82e6c` stands

Server, 500-token prompt A, 852-token prompt B, `cache_prompt` off:

| request | tok/s |
| --- | --- |
| A cold | 62 |
| A again, nothing generated between | 314 |
| B after A | 105 |
| B again | 118 |
| A after a request that generated 48 tokens | 80 (3.8–6.3 s, varies) |
| decode, last 128 of 256 | 15.32 |

Two causes, both measured:

- Prefill admission never evicts (`expert-cache.h`, `prepare_prefill_admit`).
  The first prompt fills the 54 GB arena. Repeating B cut its misses only
  from about 8164 to 7045.
- After decode the card is at 15.9 of 16.3 GB and GTT grows by about
  1.2 GB. The next prompt's expert GEMM is 6–10× slower per expert. With
  3 GB left free beside the decode cache, that prompt took 3834 ms instead of
  6211 ms, and decode fell to 14.10 tok/s (1112 slots).

## The prompt after decode: a 1.5 GB buffer landed in GTT

`fdinfo` of the server process, mix of A (500), A + 48 generated tokens,
B (852), A, on `ef82e6c`:

| moment | process VRAM | process GTT |
| --- | --- | --- |
| after decode sized its cache | 15274 MB | 16 MB |
| B prefill starts | 15415 MB | 689 MB |
| B batch 2 | 14138 MB | 2651 MB |

VRAM fell by 1.3 GB while GTT grew by 2 GB, with the card at 13.6 of
16.3 GB. That is not an eviction under pressure. The prefill batch buffer
grows per layer (free, then allocate the larger size). B's 512-token batch
asked for 1.53 GB after A had sized it to 1.2 GB, and the new buffer was
placed in GTT. Every later expert GEMM read it over PCIe: 30–50 ms for
about 160 experts instead of 6 ms for 260.

Leaving the decode cache smaller did not fix it reliably (6211 ms with
1339 slots on one run, 3840 ms on another, same binary). Allocating the
batch buffer at its 1.5 GB cap on first use did. The decode cache now also
sizes itself from the least free memory any prompt layer saw, so the room a
prompt releases at the phase change is not handed to decode.

| A after decode | B after decode | decode slots (llama-completion) | decode tok/s, last 128 of 256 |
| --- | --- | --- | --- |
| 6211–6262 ms before | 13308–14319 ms before | 1790 | 15.32 |
| 3924–4028 ms after (3 runs) | 10498–10668 ms after | 1765 | 15.28 |

KL gate: mean KLD 0.013127 ± 0.000954, same top 95.255 % (gate 0.013271,
94.980 %). Mixed-cache perplexity run 41295 ms, within run noise of
40745 ms. The 3.9 s that remain are host-cache misses: B and decode
evicted A's experts.

## The cold prompt is bound by the consumer, not the drive

Cold 500-token prompt on `b2fdd54`, 7.8 s. The drive alone sustains
6.7 GB/s on random 1 MB direct reads at queue depth 8–16 (40 GB read,
43 → 47 °C). The engine reads at 5.67 GB/s inside a layer and 4.69 GB/s
averaged over the time it is busy.

| change | reads in flight | cold prompt |
| --- | --- | --- |
| ring 8 (shipped) | 7.4 | 7.8 s |
| ring 32 | 14.6 | 7.8 s |
| `--ssd-vram-budget 0`, every cold expert on the CPU | | 9.2 s, 4.8 cores busy |
| 1 GB budget, all 12698 cold experts on the per-expert GPU path | | 8.0 s |

A deeper ring doubles the reads in flight and changes nothing. The ring sits
idle for about 0.8 s waiting for the consumer to release slots. With a 1 GB
budget the per-expert GPU path summed 7.53 s for 12698 experts, 0.59 ms
each: three synchronized `mul_mat` calls plus a host SwiGLU between up/gate
and down. The work is a few microseconds of GEMM; the rest is submit and
wait. Batching a layer's GPU-assigned cold experts into a few submissions
should leave the cold prompt bound by the drive, about 5.8 s.

## Batching the cold misses on a device worker

A cold miss that finds a free host-cache slot is read straight into it.
Those bytes stay put until the slot is published, so the expert does not
have to be computed while it holds a ring credit. The stream now hands such
a miss to a worker thread and keeps the slot unpublished. The worker runs
the device layer path (`device_layer`, bucketed `mul_mat`, GPU SwiGLU and
reduce) on chunks of 32 to 128 experts while the CPU computes the ring
reads. The stream joins it after the last read, adds its sum into the
output, and only then admits the slots. A failed chunk falls back to the
per-expert consumer for every expert not yet done. A session mutex keeps
the stream thread's per-expert matmul and ahead calls off the worker's.

The first version ran the batch after the loop: 9.3 s. The worker made it
7.3 s. The chunks then spent 30–57 ms of 33–60 ms in `ggml_vk_write_ranges`:
a memcpy into staging at about 9.5 GB/s, then a 25 GB/s transfer. Four
memcpy threads gave the same 10 GB/s. The batch buffer is mapped ReBAR
memory, and a memcpy straight into it runs at about 24 GB/s (98 MB in
4 ms). With that, the GPU share that won moved to all of these misses:

| budget, GPU share | cold prompt |
| --- | --- |
| 256 MiB, per-expert path (`b2fdd54`) | 7807 ms |
| 256 MiB, worker, staged copy | 7325 ms |
| 512 MiB, worker, staged copy | 6521 ms |
| 1 GiB, worker, staged copy | 7782 ms |
| 512 MiB, worker, direct copy | 6456 ms |
| 1 GiB / 2 GiB, worker, direct copy | 6404 / 6392 ms |
| deferred misses ignore the budget, direct copy | 6399–6426 ms, 0.97 cores busy |

So these misses no longer count against `--ssd-vram-budget`; they use the
prompt batch buffer. Budget 0 still keeps every expert on the CPU.

Deferring a layer's few late misses (pass 2 of the warm prompt) added a
second device call with about 2.2 ms of fixed scatter and reduce after the
last read, and cost 30–50 ms per prompt. A layer now defers only if at
least 32 misses can go.

| | `b2fdd54` path (switch off, same binary) | now |
| --- | --- | --- |
| cold 500-token prompt, server | 7896 ms | 6391 ms |
| warm passes 2, 3 | 1556, 1551 ms | 1554, 1543 ms |
| server: cold A, warm A, then 128 generated | 7803 / 1550 ms, 10.66 tok/s, 1365 slots | 6384 / 1535 ms, 10.69 tok/s, 1367 slots |
| mixed A, A, B, A | 7876, 1567, 7124, 2998 ms | 6420, 1551, 7197, 3076 ms |
| one-shot `llama-completion` prompt, decode last 128 | 8740 ms, 14.67 tok/s, 1766 slots | 7196 ms, 14.20 tok/s, 1382 slots |

B and the last A miss into a full cache and read through the ring, so they
do not change. The one-shot completion is the one cost: its cold prompt
never used the 1.5 GiB batch buffer before, and the decode cache took that
room. A server allocates the buffer on its first warm prompt anyway, and
there the decode cache is the same size either way.

KL gate: mean KLD 0.013388 ± 0.000911, same top 95.529 ± 0.409 %,
PPL(Q)/PPL(base) 0.990. An earlier build of the same change measured
0.014199 ± 0.000951 and 95.020 %. Both are within the error of the gate
(0.013271 ± 0.000973, 94.980 %). More cold experts now take the device
math, which the CPU reference does not use. Mixed-cache perplexity run
40073 ms, as before. ctest: 123 of 123 pass.

## Fused hyper-connection shaders, back on

`ggml-vulkan` had `DSV4_HC_PRE` and `DSV4_HC_POST` shaders, but
`supports_op` returned false: they moved the warm prompt's near-tie first
token. Decode's dense graph per layer (perf logger, one token) was 525 us
of GPU time, and only about 240 us of that reads weights. The rest is about
30 small ops at 4–10 us each. The fused ops replace the sigmoid gate, the
stream mean and the scatter-add with three dispatches. They are now claimed
for contiguous f32 operands; `test-backend-ops` passes for both against
the CPU, and the strided variants stay on the plain graph.
